## 1. Executive Summary

Phase G.4.4R resolves critical data-loss, uninstallation lifecycle, mutex handling, and version comparison defects identified during security and reliability reviews of the AttendPlan Windows installer.

All changes strictly uphold AttendPlan's non-negotiable domain rules:
- **Zero Real Data Loss**: The developer's live academic database containing **5 semesters, 76 courses, 3,584 attendance observations, 30 observation batches, 12 attendance snapshots, 181 snapshot rows, and 5 continuous evaluation snapshots** was verified with `PRAGMA integrity_check = [('ok',)]` and completely preserved. An external consistent safety backup was created outside the local application directory prior to any implementation.
- **Protected User Data by Default**: Removed the hazardous directory-wide `DelTree` on `{localappdata}\AttendPlan` in Inno Setup. Uninstallation now exclusively removes application binaries, shortcuts, and registry uninstaller keys. User attendance data, settings, and backups remain 100% intact unless an explicit, multi-step maintenance reset is executed.
- **Strict Allowlist Deletion & Permanent Directory Protection**: Implemented strict allowlist deletion in `backend/launcher.py` (`--reset-app-data`). The reset engine requires `--confirm DELETE` and a pre-verified external backup via the SQLite Online Backup API. Crucially, the directories `support_evidence/` (holding sensitive incident triage evidence) and `backups/` are permanently protected against deletion.
- **Accurate Win32 Mutex Semantics**: Corrected single-instance detection in `backend/launcher.py` by checking `kernel32.GetLastError() == 183 (ERROR_ALREADY_EXISTS)` and immediately closing duplicate handles.
- **Semantic Versioning in Pascal Script**: Replaced naive lexicographical string comparisons with integer-based semantic versioning (`CompareSemanticVersions`) in `installer/attendplan_setup.iss`, guaranteeing that `beta.10 > beta.8` and GA releases take precedence over prereleases.
- **Release Qualification**: All 375 backend tests, 14 sanitization tests, 45 frontend tests, frontend typechecks, and production bundle builds passed with zero errors.

## 2. Root Cause Analysis & Defect Remediation

### Defect 1: Uninstaller Directory-Wide Deletion Risk
- **Root Cause**: In `installer/attendplan_setup.iss`, the uninstaller hook `CurUninstallStepChanged(usPostUninstall)` contained a broad `DelTree(ExpandConstant('{localappdata}\AttendPlan'), True, True, True)`. If a student uninstalled AttendPlan to repair an issue or upgrade, their entire historical attendance database, multi-semester courses, authentication preferences, offline backups, and triage evidence would be wiped without warning.
- **Remediation**:
  1. Completely removed the `DelTree` call on `{localappdata}\AttendPlan`.
  2. Uninstallation now strictly cleans up `{app}` (the executable binary folder), Start Menu shortcuts, and registry entries.
  3. Added an explicit information dialog informing the user that their data, database, and settings remain preserved in `%LOCALAPPDATA%\AttendPlan` for future installations.
  4. Moved all data reset and maintenance capabilities into the dedicated interactive utility (`AttendPlan-Maintenance.cmd`).

### Defect 2: Missing Protection for `support_evidence/` and `backups/`
- **Root Cause**: Reset mechanisms treated `%LOCALAPPDATA%\AttendPlan` as a monolith. However, this directory contains critical non-transient folders:
  - `support_evidence/`: Encrypted/scrubbed incident triage evidence packages generated for GitHub issue support.
  - `backups/`: Historical safety backups generated by the application or maintenance scripts.
- **Remediation**:
  1. Established a strict **Deletion Allowlist** in `launcher.py`:
     - Allowlisted Files: `attendplan.sqlite3`, `attendplan.sqlite3-wal`, `attendplan.sqlite3-shm`, `settings.json`, `startup.json`, `term_calendars.json`, `totp_metadata.json`.
     - Allowlisted Dirs: `logs`, `run`, `chrome-profile`.
     - Explicitly Protected Dirs: `backups`, `support_evidence`.
  2. Any folder or file outside the allowlist is preserved.

### Defect 3: Naive Win32 Mutex Handle Evaluation
- **Root Cause**: Win32 `CreateMutexW` returns a valid handle even if the named mutex already exists. In earlier code, checking `if not handle:` was insufficient to detect if another instance owned the mutex.
- **Remediation**:
  1. Configured `ctypes.wintypes` prototypes for `CreateMutexW` and `CloseHandle` in `backend/launcher.py`.
  2. Checked `kernel32.GetLastError() == ERROR_ALREADY_EXISTS (183)`.
  3. If `183`: immediately closed the duplicate handle and returned `(is_owner=False, already_exists=True)`.
  4. Added dedicated `release_app_mutex()` to cleanly close the handle upon application shutdown.

### Defect 4: Lexicographical Version Sorting in Inno Setup
- **Root Cause**: Inno Setup previously used `CompareText(InstalledVer, '{#MyAppVersion}')`. In ASCII, `'1' < '8'`, meaning `0.1.0-beta.10` evaluated as *older* than `0.1.0-beta.8`, wrongly triggering an upgrade prompt on a downgrade or vice versa.
- **Remediation**:
  1. Implemented `CompareSemanticVersions(V1, V2: String): Integer` in Pascal script.
  2. Parses `Major`, `Minor`, and `Patch` as integers.
  3. Separates prerelease tags (e.g. `beta`) and prerelease numbers (e.g. `9`).
  4. Follows SemVer 2.0.0 precedence: GA releases > prerelease tags (`0.1.0 > 0.1.0-beta.9`), and integer sorting on prerelease numbers (`beta.10 > beta.9 > beta.8`).
  5. Wired into `InitializeSetup()`:
     - Version equality (`CmpRes = 0`): Reinstalls/repairs binaries, keeping data.
     - Older version (`CmpRes < 0`): Upgrades in-place, keeping data.
     - Newer version (`CmpRes > 0`): Warns user of downgrade risks and requires explicit confirmation.

### Defect 5: Maintenance Script Discrepancies & PII Masking
- **Root Cause**:
  - `AttendPlan-Maintenance.ps1` referenced `chrome_profile` with an underscore, while the real runtime profile created by Playwright was `chrome-profile` with a hyphen.
  - Settings parsing looked for `has_saved_mobile` and `masked_mobile`, which are API response DTO fields rather than raw keys in `settings.json` (`saved_mobile_number`).
  - Mobile numbers could be displayed in cleartext in the maintenance terminal.
- **Remediation**:
  - Corrected directory targeting to `chrome-profile`.
  - Cache cleanup deletes only temporary browser cache, code cache, GPUCache, and log files, strictly preserving session storage and cookies.
  - Parsed real JSON fields (`saved_mobile_number`, `auto_mobile_autofill`, etc.).
  - Added deterministic regex masking to hide all but the last 4 digits (`******9050`).
  - Standard uninstaller execution uses quoted paths and argument splitting with `Start-Process -Wait`.
